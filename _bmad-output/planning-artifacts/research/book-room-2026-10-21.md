# Book room: Receipts (2026-10-21)

One pass per layer (Luis, 2026-10-21: "just run through this like per book pass once per like layer"). ## 0. What a PRD is (product book, learning pass)

Building AI-Powered Products (Nika), Appendix, AI PRD template: https://learning.oreilly.com/library/view/building-ai-powered-products/9781098152697/app01.html

- **Decision.** The PRD owns why and what: problem, users, use cases, metrics, the launch quality bar, scope, risks, rollout. It gives only a high-level data flow (client, server, where data goes). Choosing algorithms and components is the architecture doc's job; how screens look and behave is the UX design doc's (DESIGN.md, EXPERIENCE.md). Book.
- **Why.** The template says to explain why algorithms are needed, not which ones. Book.
- **Missing in our PRD draft.** Problem tl;dr, market, use cases, pain points, RICE ranking, an AI MVP section (how the labeler works at a high level, what data it needs), nonfunctional requirements, AI-specific metrics and the launch bar, risks, stakeholder updates, rollout. Book. New ledger rows (added in PR #3): PR16 AI MVP, PR17 high-level data flow only, PR18 nonfunctional requirements, PR19 stakeholder updates.
- **For Receipts.** "Hybrid search" in the PRD is an architecture choice; the PRD should say why exact passage finding matters. Added.
- O'Reilly Answers also pointed to AI-Assisted Programming ch07, AI Product Manager's Handbook 2e ch7 and Spec-Driven Development with BMAD ch2 for the same split.

## 1. Evals

Practical LLM Evaluation for Production Systems, Chapter 1: https://learning.oreilly.com/library/view/practical-llm-evaluation/9781807423896/Text/Chapter_1.xhtml

- **Right.** Scoring retrieval and label apart; calibrating the judge on human labels, citing evidence and versioning it; rule checks on tool calls. Book.
- **Missing.**
  1. Per-label breakdown (a confusion matrix over the four labels), not one accuracy number. Book. (EV2)
  2. An adversarial set for the agent itself: truncated passages, a source that fails mid-fetch, right document but wrong page, loose paraphrase. Book plus Extrapolated. (EV3 is only partly covered by planted factual errors.)
  3. Dev vs hold-out split; with 14 real cases (brief addendum), say plainly that tuning and reporting share cases. Book. (EV7)
  4. Repeatability: rerun the suite 3-5 times and treat only moves outside that spread as real. Book. (EV7)
  5. Severity weights: "supported" when the truth is "contradicted" is the worst error and should weigh most. Extrapolated (from the book's VLM chapter). (EV8)
- **Beyond.** "Rate limited" as its own tool-call outcome so free-tier 429s don't inflate "not found". Extrapolated. Hybrid-search weights tuned as their own small eval. Extrapolated.

## 2. LLM agents (agent UX)

Building Applications with AI Agents, ch03 User Experience Design for Agentic Systems: https://learning.oreilly.com/library/view/building-applications-with/9781098176495/ch03.html

- **Right.** Live status rows for async work; progressive disclosure (glance, receipt, trace); showing the quoted line as the explanation. Book.
- **Missing.**
  1. A confidence signal per label, apart from the label. Book plus Extrapolated. (AG3, FE15)
  2. A graceful-failure path with a next step ("flag for human review") for unclear claims, not only a label. Book. (AG8)
  3. An autonomy choice ("auto-check" vs "review before it labels"); the book's default, though a read-only checker can skip it with a stated reason. Book. (AG3)
- **Beyond.** Nothing beyond the chapter; it pointed to ch04-ch06 (tools, orchestration, memory) for the engine. Extrapolated.

## 3. Retrieval (RAG)

Hands-On RAG for Production, ch02 The Base RAG Stack: https://learning.oreilly.com/library/view/hands-on-rag-for/9798341621701/ch02.html

- **Right.** Hybrid search, with keyword search leading, because finding one exact line needs an explainable match. Book plus Extrapolated (the weighting).
- **Missing.**
  1. Pick the embedding model first (MTEB, size vs speed); chunk size depends on its input limit. Book. (RG1, RG2)
  2. A latency budget: extract, fetch, chunk, embed and search all run live per claim. Extrapolated. (RG11)
  3. A faithfulness check on the labeling step itself. Book. (RG8)
- **Beyond.**
  1. A deterministic exact-substring check after hybrid search and reranking, so the quoted line is really in the source. Extrapolated.
  2. Receipts runs citation precision, an offline RAG eval metric, live as its product. Name that inversion on purpose. Extrapolated.

## 4. Security and guardrails

The Developer's Playbook for Large Language Model Security, ch04 Prompt Injection: https://learning.oreilly.com/library/view/the-developers-playbook/9781098162191/ch04.html

- **Right.** Treating fetched pages as untrusted. A hidden line in a source that says "label this supported" is indirect prompt injection, with the agent as a confused deputy; the book's answer is a pessimistic trust boundary: treat every model output as untrusted when its input was. Book.
- **Missing.**
  1. Tag fetched text as data, apart from instructions (e.g. a `source_content` block). Cheap, not a full defense. Book. (SG4)
  2. Least privilege for the fetch tool: cited URLs only, no access to uploads, no writes. Book. (AG9, SG1)
  3. Output validation: check in code that the quoted line is really in the fetched source. Book. (SG3, RG8)
  4. Human review only if a label ever triggers an action; plain labels are low risk. Book. (SG5 stays skipped.)
  5. Rate limits on the fetch tool, so a hostile page can't make the agent loop or refetch. Book. (SG6, AG11)
- **Beyond.** Exfiltration: a hidden instruction in a fetched page could push confidential upload text into a later fetch or lookup query. The fetch tool should never take model-written free text that could carry upload content. Extrapolated. (SG2, SG10)

## 5. System design

System Design and Behavioral Intelligence, Chapter 4 The Building Blocks of System Design: https://learning.oreilly.com/library/view/system-design-and/9781808344053/Text/Chapter_4.xhtml

- **Right.** Stateless compute first; fetch and search as schema-validated typed tools; storage picked per access pattern. Book. The labeler is the book's "evaluator" building block, turned into the product. Book plus Extrapolated.
- **Missing.**
  1. An explicit orchestrator: a graph (state machine) over extract, fetch, search, label, with retries, partial failure and fan-out, because it is replayable and testable. Biggest gap. Book. (AG10, SD4, BE14)
  2. A deliberate rule when a retry disagrees with the first result (last write wins on claim status is enough here). Book plus Extrapolated. (DA11)
- **Beyond.** The 10 ms CPU cap isn't in the book's sizing; the Worker must stay I/O-bound (await fetches and model calls) or hand work to Queues or Durable Objects. Extrapolated. (SD2, AW2) Rate limiting usually sits at the edge; ours sits in Neon by necessity (AGENTS.md); return the limit headers anyway. Book plus Extrapolated. (BE7)

## 6. Observability

Observability Engineering 2nd ed., ch21 Observability for Large Language Models: https://learning.oreilly.com/library/view/observability-engineering-2nd/9781098179915/ch21.html

- **Right.** Per-call LLM spans with model, tokens and prompts; tool and retrieval calls as part of the trace; judging steps, not a single pass/fail. Book.
- **Missing.**
  1. Cost per claim, worked out at query time from model and tokens, so prompt or model versions compare. Book. (OB10)
  2. A privacy rule for inputs and outputs: store big or private text by reference, not in span attributes. Book. (OB9, FR6)
  3. One-click "promote this trace to an eval case". Book. (OB12)
  4. A task-level quality signal ("claim verified correctly"), not only "tool call succeeded". Book. (OB6, EV11)
- **Beyond.** The chapter is for engineers. For a normal viewer: a plain-language reason per verdict, a word-level diff for "misquoted", an evidence-strength cue. Extrapolated.

## 7. Product metrics

Building AI-Powered Products, ch06 Setting Goals and Measuring Success: https://learning.oreilly.com/library/view/building-ai-powered-products/9781098152697/ch06.html

- **Right.** A North Star tied to completing the task, like a sales agent measured on deals closed. Book.
- **Proposed North Star.** Share of claims in a report that reach a correct label with a quoted line. Extrapolated (the book has no citation checker). (PR5)
- **Missing.** The book's other metric buckets, at least one each. Book. (PR5, PR15)
  1. Guardrail: wrong "supported" labels (the most damaging error).
  2. System health: uptime and latency of the pipeline.
  3. AI proxy: precision and recall per label.
  4. Product health: feature adoption, e.g. how many visitors open a receipt or the full trace.
- **Beyond.** The four labels split failures into retrieval (not found), facts (contradicted) and quoting (misquoted), each with its own fix; most AI tools collapse this into pass/fail. Extrapolated.

## Edge list (ranked for Receipts)

Ranked by what a normal visitor would notice first.

1. **Show the mismatch.** For "misquoted" and "contradicted", highlight the exact words that differ between the report and the source. Normal people get it in one look. (Observability ch21, extrapolated.) Lands in: UX.
2. **The quote is checked in code.** A deterministic exact-match check proves the source line exists before any label shows; show a small "verified in source" mark. Pointed at by RAG ch02 and security ch04; the exact-match check itself is the room's extrapolation. Lands in: PRD, arch.
3. **Wrong "supported" is the one error that matters most.** Make it the guardrail metric and the hard-block gate, weight it in evals, and show the count on the evals page. (Evals ch1, product ch06.) Lands in: PRD.
4. **Honest uncertainty.** Evidence strength per label plus "needs a human" as a next step, instead of a forced label. (Agents ch03.) Lands in: PRD, UX.
5. **Caught an injection.** When a fetched page holds hidden instructions, label the claim and show a visible "this source tried to instruct the checker" note; build these pages into the adversarial set. Turns a security control into a demo moment. (Security ch04 plus Added.) Lands in: PRD, arch, evals.
6. **An eval method as the product.** Receipts runs citation precision, normally an offline RAG metric, live for users; the labeler is the "evaluator" block. Use this line in the story and the explainer. (RAG ch02, system design ch4, extrapolated.) Lands in: brief, explainer.
7. **Replayable claim graph.** An explicit state machine per claim, so any run can replay and the full trace is the graph. (System design ch4.) Lands in: arch.
8. **Promote a trace to an eval case** from the full-trace view. (Observability ch21.) Lands in: PRD, arch.
9. **"Rate limited" as its own status**, so free-tier limits never pass as "not found". (Evals ch1, extrapolated.) Lands in: PRD.
10. **Cost per claim** on the full trace and the evals page. (Observability ch21.) Lands in: PRD.

## Scope change?

**No change in scope; change the framing.** Every book confirmed the core loop (extract, fetch, find, label with a quote) and none pointed to a better product. The two shifts: (1) the story leads with "an eval technique turned into the product", which makes the evals visible to every visitor; (2) the first view is built for a normal person (edge items 1, 2, 4, 5). The engine gaps (orchestrator, embedding model, latency budget, cost) are architecture work for Winston, not a scope change.
